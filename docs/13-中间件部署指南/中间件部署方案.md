# DevOps 中间件部署功能 - 最终解决方案

## 🎯 总体方案概述

### 核心理念
**"模板驱动 + 用户自定义 + 命令一致性"**

中间件作为独立的基础设施服务，与应用解耦部署。用户上传自定义模板到对应平台目录，系统只负责模板选择和变量替换，最大化灵活性和可扩展性。

### 设计原则
1. **应用与中间件分离**: 中间件独立部署，可服务多个应用
2. **命令风格一致**: 复用现有devops命令模式，降低学习成本
3. **模板体系统一**: 沿用现有模板管理机制
4. **用户完全掌控**: 用户上传模板，系统只做变量替换

## 🔧 命令设计

### 基本命令结构
```bash
# 使用模板名称作为中间件类型，保持与现有应用部署命令一致
devops run middleware <template-name> <instance-name> [OPTIONS]

# 示例
devops run middleware redis-standalone cache-server
devops run middleware mysql-ha main-db --storage 100Gi
devops run middleware kafka-cluster message-queue --replicas 3
```

### 通用参数选项

#### 基础参数
```
--template TEMPLATE     指定模板名称 (如: redis-cluster)
--workspace WORKSPACE   指定工作空间
--namespace NAMESPACE   指定K8s命名空间
--platform PLATFORM     指定部署平台 (kubernetes|docker-swarm|docker-compose)
--version VERSION       指定中间件版本
-i, --interactive       交互式配置模式
--dry-run              仅预览配置，不执行部署
--force                强制执行，跳过确认
```

#### 资源配置
```
--cpu-request CPU       CPU请求量 (如: 200m)
--cpu-limit CPU         CPU限制 (如: 1000m)
--memory-request MEM    内存请求量 (如: 512Mi)
--memory-limit MEM      内存限制 (如: 2Gi)
--storage SIZE          存储大小 (如: 10Gi)
--storage-class CLASS   存储类型 (如: fast-ssd)
```

#### 高可用配置
```
--mode MODE            部署模式 (standalone|master-slave|cluster)
--replicas COUNT       副本数量
--backup-enabled       启用自动备份
--monitoring-enabled   启用监控
```

### 2. 扩展模板查找逻辑（修改现有函数）
```bash
# 扩展现有的find_template_dir函数
function find_middleware_template() {
    local platform_dir="$1"
    local template_name="$2"

    # 查找顺序：工作空间模板 → 全局模板
    local workspace_template="$cfg_workspace_path/middleware/templates/$platform_dir/$template_name"
    local global_template="$DEVOPS_ROOT/middleware/templates/$platform_dir/$template_name"

    if [[ -d "$workspace_template" ]]; then
        echo "$workspace_template"
    elif [[ -d "$global_template" ]]; then
        echo "$global_template"
    else
        return 1
    fi
}
```

- **定制化程度高**: 可以针对特定需求创建专用模板

### 4. 架构清晰
- **职责分离**: 中间件独立部署，与应用解耦
- **生命周期独立**: 中间件可服务多个应用
- **维护简单**: 模板由用户维护，系统只负责执行

### 5. 风险可控

- **兼容性好**: 不影响现有功能，可以渐进式推广

#### 最佳实践建议

1. **模板命名规范**
   ```bash
   # 推荐的模板命名方式
   redis-standalone      # Redis单实例
   redis-cluster        # Redis集群
   mysql-standalone     # MySQL单实例
   mysql-ha            # MySQL高可用（主从）
   elasticsearch-cluster # ES集群
   kafka-cluster        # Kafka集群
   ```

2. **变量设计原则**
   ```yaml
   # 在metadata.yaml中合理设计变量
   variables:
     # 必填变量尽量少
     - name: "cluster_name"
       required: true

     # 提供合理的默认值
     - name: "memory_limit"
       default: "1Gi"

     # 提供选项列表
     - name: "persistence_type"
       options: ["rdb", "aof", "both"]

     # 提供验证规则
     - name: "replicas"
       validation: "{{ value >= 1 and value <= 10 }}"
   ```

3. **Jinja2表达式使用建议**
   ```yaml
   # 适合使用Jinja2的场景：
   # 1. 动态生成列表
   {% for i in range(replicas | int) %}
   - {{ instance_name }}-{{ i }}
   {% endfor %}

   # 2. 条件配置
   {% if environment == 'production' %}
   backup_enabled: true
   {% endif %}

   # 3. 计算配置值
   {% set heap_size = (memory_limit | regex_replace('Gi', '') | int * 512) %}
   heap_size: {{ heap_size }}m
   ```

4. **端口配置最佳实践**
   ```bash
   # 复用现有端口配置机制
   --service-port "6379"           # 内部服务端口
   --export-port "30379"           # 外部访问端口
   --app-port "6379"              # 应用端口（向后兼容）

   # 多端口配置
   --service-port "9200,9300"      # ES的HTTP和传输端口
   --export-port "30920,30930"     # 对应的外部端口
   ```

这样的设计既保持了简单性（通用变量开箱即用），又提供了极大的灵活性（模板特定变量完全可定制），同时复用了现有的端口配置机制，并通过Jinja2表达式支持解决了复杂配置生成的问题。
